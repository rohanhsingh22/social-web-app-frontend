# HiRotoli — Complete Page-by-Page UI Blueprint

**Version:** 2.0 · **Status:** Proposed visual specification for agent implementation · **Scope:** Launch 1 web, desktop/tablet/mobile · **Source of truth:** Latest uploaded frontend ZIP plus the existing HiRotoli UI Design System v1.0. This is a **design proposal**, not a claim that every visual element is implemented today. Preserve existing routes, business rules and API contracts.

> **Agent entry point:** Read sections A–D and the target page specification before editing. Implement shared foundations first; change one page family at a time; compare light/dark and mobile/desktop; do not invent missing backend functionality. Where the current code conflicts with this proposed design, document the conflict and get product approval for navigation or feature changes.

## A. The intended finished product — one mental picture

HiRotoli feels like a welcoming digital social lounge, not an enterprise dashboard or a gaming clan portal. It has a **stable left navigation**, an airy main reading/conversation surface, optional contextual right rail and a single recognizable accent selected by the user. Content is visually calm; personality comes from people, five Toli identities, and a small amount of tasteful brand color. The default illustration in this document assumes **dark mode + rose accent**, but every screen must work with light/dark/system and all five accents.

**Desktop snapshot (conceptual):**

```text
┌───────────────────────┬────────────────────────────────────────────┬──────────────────────────┐
│ HiRotoli logo         │ Page heading + page-specific action        │ Context (only if useful) │
│                       │ ───────────────────────────────────────── │                          │
│ Home                  │ Main content: feed / conversation / cards  │ Suggestions / tips       │
│ Chats                 │                                            │                          │
│ Thoughts              │                                            │                          │
│ Connections           │                                            │                          │
│ Notifications         │                                            │                          │
│ Settings              │                                            │                          │
│ ─ Channels ─          │                                            │                          │
│ Public rooms          │                                            │                          │
│ My Toli (if chosen)   │                                            │                          │
│                       │                                            │                          │
```

**Mobile snapshot:** fixed compact top header, one full-width content column, five-item bottom navigation **proposed, requires approval**, profile/menu sheet for secondary settings, drawers for room lists and context, and sticky composers above the safe-area/bottom nav. No essential action is desktop-only.

**North-star feeling:** friendly, readable, social, trustworthy. **Avoid:** random page-specific gradients, glowing neon, competing typefaces, glassmorphism, inconsistent icon sizes, cramped feeds and oversized decorative hero cards on everyday utility screens.

## B. Exact global visual contract

| Element | Proposed default | Rules |
|---|---|---|
| Desktop sidebar | 256px, fixed | Same logo, nav row height, active state, channel grouping and user menu on all authenticated routes |
| Desktop content gutter | 24–32px | Page max-width 1180–1280px except full-height chat layouts |
| Main feed column | 640–720px | Readable text measure; never stretch individual Thoughts across an ultrawide display |
| Context rail | 288–320px | Only on pages with valuable content; collapses below 1200px |
| Page header | 28px desktop / 24px mobile | Left aligned, predictable title/subtitle/action positions |
| Body | 15–16px, line-height 1.5–1.6 | Never below 14px for substantive content |
| Page canvas | `--background` | No per-route background colors |
| Primary surface | `--surface` | Consistent cards, sidebar and dialog foundations |
| Nested surface | `--surface-muted` | Inputs, composer, secondary panels |
| Border | `--line` 1px | Prefer quiet borders to large shadows |
| Primary radius | 16px | Inputs/buttons 12px, dialogs 20–24px |
| Primary action | `--brand` | User accent; only one visually dominant CTA per local section |
| Touch target | at least 44×44px | Every icon-only control must have accessible name |
| Page section spacing | 24–32px | Cards 12–16px apart; internal card padding 20–24px desktop, 16px mobile |
| Animation | 120–240ms | Respect reduced-motion; no animated backgrounds behind text |

**Existing theme foundation:** `--background` light `#f6f7fb`, dark `#0e1018`; `--surface` light `#fff`, dark `#161927`; `--ink` light `#1a1c2e`, dark `#f3f4fb`; `--line` light `#e4e7f0`, dark `#272c40`. Existing accent choices: rose `#ff2e63`, violet `#7c3aed`, blue `#2563eb`, emerald `#10b981`, amber `#f59e0` (light-mode values; use current dark adjustments). **Do not replace current token implementation without verifying it.**

**Identity hierarchy:** displayName first, profile picture second, optional Toli badge third, handle/metadata subdued. The 3D character belongs on Home and character-related surfaces, **never** substitutes for social profile photo. Five Tolies: Vector, Wave, Quantum, Orbit and Flux. Proposed Toli hues: blue, teal, violet, amber and coral respectively; check current avatar artwork before finalizing.

**Universal states on every data-driven page:** initial skeleton matching final geometry; empty with a single useful CTA; inline recoverable error with Retry; offline banner without discarding composed text; optimistic action pending; permission-restricted state; success feedback; keyboard focus; mobile loading and error layouts. All timestamps should be human readable with exact time in tooltip/details.

## C. Site map and route ownership

The latest frontend includes `login-page.tsx`, `auth-callback-success-page.tsx`, `onboarding-page.tsx`, `home-page.tsx`, `thoughts-page.tsx`, `thought-thread-page.tsx`, `chat-page.tsx`, `channel-page.tsx`, `messages-page.tsx`, `direct-message-page.tsx`, `connections-page.tsx`, `notifications-page.tsx`, `profile-page.tsx`, `settings-page.tsx` and `not-found-page.tsx`. **Use the router's actual path strings; do not infer paths from filenames.** Public/Toli channel pages may be route variants of the same component. Report and block UI may be dialogs/sheets rather than dedicated routes.

### Navigation rules

- Primary destinations: Home, Chats, Thoughts, Connections, Notifications and Settings (existing desktop). Profile via identity/user menu. Channels grouped below navigation; Toli room only for a selected Toli.
- Desktop sidebar retains its position and active styling while content changes. Mobile navigation remains visible on root screens and is hidden/replaced with back navigation only where necessary for full-screen message composition.
- Navigation changes are product decisions: the proposed five-item mobile bar and relocation of Settings require explicit approval. Until then, preserve existing behavior and improve sizing/accessibility without silently deleting destinations.
- Search is page-scoped unless an existing global-search API is confirmed. Do not display fake global search functionality.

## D. Reusable component anatomy and behavior

**PageHeader:** eyebrow optional; title; one-line subtitle optional; right action; tab bar underneath. Desktop left aligned; mobile title/back/action in 56–64px header. **PersonRow:** 40–48px profile photo, displayName, optional Toli badge, one-line secondary text, contextual action. **ThoughtCard:** author row, body, optional topic chips, interaction row, overflow actions, no media. **ChatBubble:** avatar only at grouping boundary, displayName in rooms, body, timestamp and delivery/error status where supported. **ConversationRow:** profile photo, name, last message, timestamp, unread badge if available. **NotificationRow:** category icon, actor if applicable, body, relative time, unread marker, target click. **EmptyState:** 48px icon, 18–20px heading, 1–2 lines explanation, optional action. **SafetyDialog:** action-specific title, reason selection/text if existing API supports, cancel and explicit confirm.

**Interaction vocabulary:** hover changes background subtly; active nav uses soft accent fill and 2–3px visual marker or clear selected state; focus ring is accent plus contrast outline; disabled lowers emphasis without hiding label; destructive actions use danger tokens and confirmation. Use consistent 20px icons and 8px icon/label gap; only social reactions may use compact 18px icons within 44px hit targets.

**Agent checklist:** verify OAuth buttons and redirects; never reveal token/session details; test keyboard activation, popup blocked/cancelled flow and small 320px screens.

## 02. Onboarding / display name / interests / Toli

**Existing implementation entry points:** `src/pages/onboarding-page.tsx; src/components/toli/*`. Verify exact component and route ownership in the current repository.

**Purpose:** Introduce a new user to the social identity and choices without making setup feel like a form marathon. Use a narrow centered wizard (max 720px) with a simple 3–4-stage progress indicator matching actual onboarding steps; do not add unimplemented steps. Each step has one dominant decision, supporting explanation and a persistent Back/Continue footer.

**Identity step:** 96px profile photo preview with provider avatar; prominent displayName input and helper text describing uniqueness. Show availability feedback only if backend supports it. Handle inline errors, forbidden names and saving state. Never show OAuth provider display name as the public identity after onboarding.

**Interests step:** selectable pill grid with 44px targets; selected pills use brand-soft fill and check icon; show optional/required status accurately based on current validation. **Toli step:** five equal cards: Vector, Wave, Quantum, Orbit, Flux. Each card displays name, distinct motif, one-line personality copy (marketing only), a few matching avatar thumbnails if available and a selected border. A clear “Skip for now” option is as prominent as the ability to proceed without membership. One Toli only; do not add rankings or invitations.

**Avatar step (if existing):** grid of exactly five static avatars belonging to chosen Toli, with large selected preview; provider-avatar option if supported. **Desktop:** two-column Toli grid plus one full-width final card; **mobile:** one column or two compact cards depending on width. **Completion:** welcome confirmation, chosen identity summary and CTA to enter Home/public chat. **States:** step validation, back-navigation preserving selections, save failure, existing incomplete onboarding, Toli changed invalidating an old Toli avatar.

**Visual QA for this screen:** compare at 1440×900, 1024×768, 768×1024, 390×844 and 320×700; check light and dark, all five accents where applicable, long names, empty data, loading, error, keyboard navigation and touch targets.

**Existing implementation entry points:** `src/pages/thoughts-page.tsx; thoughts feature components`. Verify exact component and route ownership in the current repository.

**Purpose:** The editorial heart of HiRotoli: discover people through short, text-only writing. Layout should feel like a readable conversation feed, not an imitation of X's crowded metric-driven UI. Main column 640–720px, optional contextual rail 288–320px only when populated.

**Exact vertical anatomy:** shared page heading “Thoughts” + short subtitle; compact primary “Write a thought” action on mobile; sticky feed tabs **For You / Fresh / Connections / Me** (preserve current implementation); composer card (avatar 40px, expandable textarea, character counter if limit exists, topic chips if supported, one brand-accent Post button); feed status strip if needed; Thought cards with 16px vertical gap; pagination sentinel and end-of-feed state.

# F. Cross-screen interaction flows (must look like one product)

## Flow 1 — New user to first conversation
Login → OAuth callback → onboarding identity → optional Toli choice/avatar → Home → public room directory → room → user profile → send connection request. Same person avatar, displayName and Toli badge on every surface. Each screen keeps consistent navigation and Back behavior. User who skips Toli can still enter public rooms and post Thoughts.

## Flow 2 — Thought to friendship
For You → open Thought detail → read comments → open author profile → connect → received/accepted state → DM inbox → thread. Thought cards and profile cards share PersonRow identity; relationship action labels remain synchronized. Hide/report remove or restrict content consistently without leaking through other feed tabs.

## Flow 3 — Toli membership change
Settings or onboarding selection → Toli cards → selected avatar → confirm → current badge and My Toli room update. Previous room must no longer be accessible through stale navigation or open socket. If avatar is invalid for new Toli, prompt to choose a new avatar before confirming or fall back per existing business rules.

## Flow 4 — Notification to action
Bell unread badge → Notifications page → connection request row → Accept → accepted connections → DM. Optimistic unread count and actual list remain consistent; never mark everything read merely by opening the bell unless current product explicitly requires it.

## Flow 5 — Offline chat and recovery
Open room/thread → connectivity drops → banner and composer remain → Send disabled or queued only if queue semantics exist → reconnect → retrieve missed messages, dedupe by ID, restore scroll. No fake “sent” state when server has not acknowledged persistence.

# HiRotoli — Unified UI Design System & Complete Product Interface Specification

**Version:** 1.0 · **Status:** Proposed design standard for implementation · **Scope:** Launch 1 web app · **Basis:** latest uploaded frontend ZIP (`social-web-app-frontend-main (1).zip`) and previously agreed HiRotoli product scope.

> **For every design or coding agent:** Read this entire document before modifying a screen. This document is the proposed single source of truth for UI decisions. Preserve the current feature behavior and API contracts. The sections marked **Existing** describe code inspected in the uploaded frontend; **Standard** defines the design we are adopting. Do not mistake a proposed specification for an already-implemented feature.

## 1. Product identity and design objective

HiRotoli is a social space where strangers can enter public rooms, talk first, connect later, join one of five Tolies, share text-only Thoughts, and message connections privately. The interface must feel welcoming, conversational, contemporary and trustworthy—not like an enterprise CRM, competitive gaming dashboard, or an X/Twitter clone. The 3D character is a distinct home experience, not the user's social profile photo.

**Design principles:**
1. **One recognizable shell.** Navigation, headers, panels and controls look and behave consistently across every route.
2. **Conversation first.** Chat and Thoughts maximize reading space; decorative visuals never overpower content.
3. **Person before metrics.** Names, profile photos, Toli identity and message content precede counts.
4. **Quiet surfaces, expressive identity.** Restrained neutrals; the chosen accent highlights interaction. Toli identity is separate from the global accent.
5. **Predictable states.** Loading, empty, error, offline, restricted, pending and success states have standard patterns.
6. **Mobile is a full experience.** No desktop-only essential action; drawers and panels adapt rather than disappear.
7. **Accessible by default.** Keyboard support, readable contrast, visible focus, reduced motion and screen-reader announcements.

### 1.1 What already exists in the uploaded frontend

The inspected code contains `AppShell`, responsive desktop left navigation/mobile bottom navigation, theme and accent preferences, reusable UI primitives, the 3D Home, Thoughts (For You/Fresh/Connections/Me), channels, DMs, connections, notifications, onboarding, profile and settings. The current CSS already defines light/dark semantic variables and five selectable accents. **This document unifies and extends those existing patterns; it does not require a rewrite.**

### 1.2 Scope boundaries

Launch 1 includes authentication, onboarding, profile and picture choice, 3D Home, five predefined Tolies, public and Toli chat, connections, DMs, text-only Thoughts, four notification types, safety/moderation, settings and responsive navigation. **Do not add** Thought media uploads, Toli leaderboards, competitions, Toli invitations, paid tiers, elaborate badges, events or a new ML recommendation UI. Suggestions below are visual presentations of existing features, not permission to invent new backend capabilities.

## 2. Visual direction

**Creative direction:** “A lively social lounge with editorial clarity.” Clean, comfortable reading surfaces; soft rounded corners; gentle borders; purposeful color; concise language. Avoid full-screen neon gradients, dense glassmorphism, heavy drop shadows, inconsistent illustrated mascots, oversized dashboard widgets and excessive animation.

**Brand mark:** Reuse the existing light/dark HiRotoli logos in `src/assets/app-logo/`; do not recreate the logo as text in each feature. The existing blue–violet–pink logo gradient may remain a brand-only flourish. It must not replace the selected UI accent across controls.

**Theme model — Existing:** `light | dark | system`; accents `rose | violet | blue | emerald | amber`; current default `system + rose`. Preserve these values and user preferences. Use `data-accent` and `.dark` as already implemented. No feature should hardcode its own primary purple/pink in place of semantic tokens.

|---|---|---|---|

| Page heading | 28 / 24 px | 700 | 1.2 |
| Section heading | 20 / 18 px | 650 | 1.3 |
| Card heading / person name | 16 / 16 px | 650 | 1.35 |

### 3.4 Spacing, dimensions and surfaces

**Standard spacing scale:** 4, 8, 12, 16, 20, 24, 32, 40, 48, 64 px. Use these increments rather than arbitrary per-page margins. Global content gutter: 24–32 px desktop, 16 px tablet/mobile. Standard card padding: 20–24 px desktop, 16 px mobile. Card gap: 12–16 px. Section gap: 24–32 px.

**Radii:** 8 px small controls, 12 px inputs/buttons, 16 px standard cards, 20–24 px feature panels/dialogs, fully rounded pills/avatars. Current root radius is `0.75rem`; extend consistently rather than overriding everything.

**Borders:** 1 px `--line` for cards and structural dividers; stronger border for focused controls. Shadows: subtle only on overlays and floating menus; prefer borders to card shadows. Interactive minimum hit target: 44×44 CSS px for touch. Standard input/button height: 44 px; compact control 36 px only when paired with accessible hit area.

### 3.5 Motion

Use 120–180 ms hover/focus transitions, 180–240 ms drawers/dialogs, 200–300 ms optional feed entry animation. No animation on every feed item during infinite scrolling. Skeleton shimmer may be subtle. Respect `prefers-reduced-motion: reduce` and remove nonessential transforms/animated gradients.

## 4. Global information architecture and app shell

**Existing:** full-height interactive `CharacterScene`, small My Toli overlay and Toli-room entry.

**Standard:** keep the 3D character as the hero, not a miniature dashboard widget. ### 6.4 Thoughts — principal editorial feed

**Existing:** For You, Fresh, Connections, Me; composer; cards; right sidebar; local top sort and hashtag filter; infinite scroll and pull-to-refresh.

**Desktop standard:** optional 288–320 px right contextual rail; central feed max-width **680–720 px**; avoid extremely wide reading lines. Header “Thoughts” and compact create action. Tabs immediately beneath header; sticky only if scroll container behavior is reliable. Composer at top of feed: 48 px avatar, “What's on your mind?” prompt, expanding textarea, character counter if backend enforces a limit, optional topic/tag guidance only if supported, right-aligned Post button. A separate floating Post action is acceptable on mobile but must not duplicate a full-size always-visible composer unnecessarily.

**Thought card anatomy:** avatar (44–48 px), display name, handle/HiRotoli ID where applicable, Toli badge, relative timestamp, overflow menu; body 15–16 px at 1.5–1.6 line-height; hashtags as inline links; bottom engagement row in consistent order: like, comment, share, optional counts. Whole card should not accidentally trigger navigation when a user clicks an action. No media block in Launch 1. Use profile picture, never 3D character. Owner menu: edit/delete; other-user menu: hide/report. Destructive actions require confirmation where appropriate.

**Tab semantics:** For You = ranked recommendations; Fresh = chronological; Connections = connected authors; Me = own posts. Top sorting and hashtag filtering must clearly state if they only affect loaded items; do not imply database-wide sorting unless API supports it. Keep tab selection stable when opening and closing a Thought thread; preserve scroll when navigating back if practical.

**Thread:** central column with back control, parent Thought, comment composer, comments ordered according to existing API semantics, reply loading and empty states. Do not invent nested threaded replies if unsupported. Show a non-revealing unavailable state for deleted/restricted Thoughts.

**Sidebar:** concise sections such as relevant topics and “Start a conversation” / channel entry **only when data is real**. Do not fake trends or engagement counts. On mobile, hide sidebar and surface important discovery links elsewhere.

**Existing:** channel list in sidebar, chat shell, Socket.IO messages; optional My Toli channel.

Group consecutive messages by same sender within a short interval visually; preserve individual message identity for moderation. **Mobile:** room list is a separate screen/sheet; opening a room shows a back arrow, transcript and bottom composer. Avoid a permanently visible desktop room sidebar squeezing messages. Group messages, display date separators and readable timestamps. Keep sender identity visually clear in group conversations only if such conversations exist; do not invent group DMs.

**Mobile:** conversation list occupies full width; opening a DM navigates to a full-width thread. Back button returns to list with preserved scroll. Keyboard opening must not hide composer; account for safe area and visual viewport. For blocked, disconnected or unavailable contacts, show accurate messaging restriction states. User card: 48 px avatar, display name, optional handle, Toli badge, compact supporting info, one clear action. Requests group Received and Sent with status chips. Accept/decline/cancel/remove actions must have distinct hierarchy; destructive removal gets confirmation. No empty grid of oversized cards on desktop: use a comfortable responsive two-column grid when space allows, single column mobile. ### 6.8 Notifications

**Existing launch types:** connection request, accepted connection, new DM, legal notice. Do not add Thought likes or Toli activity as notification types without a product change.

**Standard:** header with unread count and Mark all as read; segmented All/Unread filter only if supported or implemented without misleading state. Each row: type icon or actor avatar, concise message, relative timestamp, subtle unread indicator and contextual destination. Rows are 72–96 px, not giant cards. Batch operations have pending/disabled states; don't optimistically claim a legal notice was read before API confirmation. Notification bell should display unread count without needing to render the full list if a dedicated endpoint is introduced.

### 6.9 Profile — own and other users

**Standard:** compact banner or gradient-tinted header using semantic tokens, large 96 px profile picture, display name, handle/HiRotoli ID, Toli badge, bio, location/language/interests only if visibility permits. Primary action on other-user profile depends on actual relationship state: Connect, Requested, Accept, Message, or restricted. On own profile: Edit profile and profile-picture control. Stats use a consistent compact row; do not inflate follower counts or invent unsupported social metrics. User Thoughts appear in a reusable list using the same `ThoughtCard` component. A profile picture is provider or valid Toli avatar; 3D character appears only in a separate optional character view if already supported.

### 6.10 Toli selection and identity

**Standard:** the five predefined Tolies are displayed as five equally weighted selection cards. Each shows identity motif, name, one short neutral description approved by product, avatar preview and selection state. A user belongs to at most one Toli. Skip is a visible neutral option. My Toli surfaces show badge, chosen avatar and entry to the authorized Toli chat room. Switching Toli requires explaining the effect on room access and validating the current avatar. Avoid ranks, levels, leaderboards, quests or competition metaphors.

### 6.11 Settings

**Existing sections:** Display, My Toli, Privacy, Account; appearance preferences and profile visibility controls.

**Standard desktop:** 240 px settings section rail + content panel max-width 680 px. Mobile: section list first, section detail second, with back navigation. Each section uses same title/subtitle, grouped cards, field labels and dividers. Display offers Light/Dark/System and five accent swatches with selected check; preview changes immediately and persist according to existing behavior. Privacy switches clearly explain audience/visibility and reflect backend values. My Toli reuses the onboarding Toli and avatar pickers, not duplicated variants. Account includes actual supported session/logout controls and profile entry. Use explicit Save when a group is not autosaved; never mix save semantics without indication. Show success and recoverable failure states.

### 6.12 Safety and moderation

Report action opens a standardized dialog/sheet with reason selection, optional explanation if supported, clear privacy and submission feedback. Block/unblock actions show consequences in concise language. Banned, muted, removed and unavailable content use consistent states without leaking sensitive moderation details. Never make report buttons decorative or imply that a report guarantees immediate action. Admin/moderation UI, if exposed in this release, should reuse tokens but may use denser data tables with a separate authenticated layout.

### 6.13 Not found, offline and error surfaces

404: simple brand-aligned illustration/icon, “Page not found,” Return home. 403/restricted: neutral explanation, safe destination. Network offline: persistent small banner on chat and actionable Retry elsewhere. 500: retry and support guidance without raw stack traces. Expired session: non-destructive sign-in flow; preserve unsent local drafts when feasible. Global error boundary must not replace the entire app shell with a blank screen.

## 7. Universal interaction-state matrix

Every data-backed screen must implement the following states consistently:

| State | Required behavior |
|---|---|
| First load | Layout-matched skeleton; no giant global spinner for a single panel |
| Background refresh | Keep existing content visible; small inline progress indicator |
| Empty | Explain why empty and show one relevant next action |
| Error | Human-readable message + Retry; preserve valid cached content |
| Offline/reconnecting | Visible status; avoid duplicate sends and lost drafts |
| Pending mutation | Disable repeated action; show spinner/label; prevent double submit |
| Success | Update visible state; toast only when confirmation adds value |
| Unauthorized | Appropriate sign-in/locked state; never show private stale content |
| Restricted/deleted | Safe unavailable state; no leaked author or content details |
| Long content | Wrapping, truncation only where appropriate; accessible expand action |

Use `aria-live="polite"` for non-urgent async updates and `role="alert"` for actionable errors. Never rely only on a toast for validation failures.

## 8. Accessibility and content standards

- WCAG 2.2 AA target for contrast, focus, keyboard navigation and touch targets. Check each accent in both themes.
- Semantic headings: one H1 per page; headings follow hierarchy. Buttons are buttons, navigation is links.
- Every icon-only control has an accessible name. Menus/dialogs trap focus and return it when closed.
- Do not rely on color alone for unread, selected, Toli identity or errors.
- Visible focus ring with adequate contrast; never globally remove outlines without replacement.
- `prefers-reduced-motion`; screen-reader announcements for new messages without flooding announcements.
- Text content wraps safely, including long usernames, URLs and emoji. Use `overflow-wrap:anywhere` where necessary.
- Timestamps use a meaningful `title`/accessible full date where possible; relative timestamps update sparingly.
- Use short, human copy. Prefer “Couldn’t load messages. Try again.” over raw HTTP/Prisma errors.
- Don't show unsupported controls or fabricated counts simply to fill a mockup.

## 9. Responsive acceptance criteria

Test at **320, 375, 390, 430, 768, 1024, 1280 and 1440 px** and at 200% zoom. No horizontal overflow. Primary controls reachable on 320 px. Bottom nav and keyboard do not cover chat input. Long Thoughts and names wrap without breaking card layout. Sidebars collapse predictably. Dialogs fit small viewports and scroll internally when necessary. Light/dark/system and all five accents must work on every route. Verify hover, touch and keyboard behavior separately.

## 11. Agent guardrails and definition of done

**Do:** work in small PRs, reuse existing components, use semantic tokens, retain RTK Query behavior, respect permissions, test each responsive breakpoint, compare screenshots against the approved design, and preserve feature flags/contracts.

**Do not:** rebuild the whole frontend in one commit; replace functional screens with static mockups; change auth, ranking or pagination while doing visual cleanup; add fake trending data; hardcode an accent color; add new notification types; convert Tolies into gaming clans; put 3D characters into social avatars; ship only a dark-mode design; or silently change navigation without approval.

**Definition of done for each screen:** matches tokens; uses standard shell/header; has mobile/tablet/desktop layouts; supports both themes and all accents; uses shared primitives; has loading/empty/error/pending/restricted states; keyboard/touch accessible; no horizontal overflow; no dead buttons; passes tests/build; screenshots reviewed at specified breakpoints; current backend integration works.
